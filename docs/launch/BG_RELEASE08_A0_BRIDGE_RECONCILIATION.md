# BG-RELEASE08-A0 — bridge template reconciliation

Live read-only comparison (founder, after the accepted API reconciliation): the latest `bizgenie-studio-bridge-staging` template differs from serving `bizgenie-studio-bridge-staging-step7-c023184c` in nine entries: eight environment settings and the container name. No deployment, traffic change or cloud mutation occurred.

## Key fact: the bridge environment is REPLACED, not inherited
`a0-deploy.sh bridge` deploys with `--env-vars-file`, which removes every existing plain environment variable and sets exactly the validated A0 file. So the eight environment differences describe the *latest template's* leftovers from earlier no-traffic candidates; none can reach the A0 revision. What **would** be inherited silently: secret-backed environment (`--env-vars-file` does not touch it), volumes, probes, resources, ports, args, service account, scaling and the container name. The comparator therefore (a) treats environment differences as superseded only when no secret-backed variable exists on either side, and (b) keeps everything else strict.

The A0 file contains exactly 22 approved names (Release 07 `workspace` profile; `PORT` is excluded — see blocker B1). `a0-deploy.sh` re-validates names and flag values before any deploy: the seven permission flags must be exactly `false`, `BG_BRIDGE_ALLOW_FOUNDER_ADDITIONAL_WORKSPACE` exactly `true`, `BIZGENIE_ENVIRONMENT` `staging`; any other name (campaign-root, LinkedIn, token-vault...) is refused.

## Partial-deployment recovery (resume)
`a0-deploy.sh api` and `bridge` are now idempotent and never deploy twice under the tag (`gcloud run deploy --tag` would silently move it):
- **Checkpoint:** an existing `a0-dfd49116` tag is adopted only if it is not the serving baseline, carries the exact accepted image digest, is Ready, receives 0% traffic, serving is still the recorded baseline, and the state (if any) names the same revision and baseline. The bridge is adopted only if its live environment equals the validated A0 file exactly and it is pinned to the accepted API revision.
- **Before deploying** the revision list is snapshotted into the state. After a failed deploy, any new revision that is untagged or unrecognised stops the run (inspect read-only); a clean failure (nothing new) may be retried once; an attempt older than 24 h with nothing verifiable is STALE and needs a human to review and remove the state file.
- **EV_TAG:** required and bound to the API revision before the bridge is deployed; a state bound to a different pair is a conflict.
Tests are synthetic only; nothing was run against Cloud Run.

## Traffic readback correction (Codex P1 on `86bc4ffb`, #191 comment 7205304764)
**Defect (reproduced):** `baseline_readback_ok()` filtered out entries with `percent <= 0` before validating the array, so a readback of the baseline at 100 % plus another revision at **-1 %** was accepted: automatic recovery printed RECOVERED without a lock, and manual rollback succeeded and cleared the lock. **Correction:** `traffic_array_ok` validates every entry before any filtering (a non-empty array of objects; each with a non-empty string `revisionName`, so tag/URL-only and `latestRevision` targets are refused; an integer `percent` in 0–100, so missing, null, string, boolean, negative, fractional and over-100 are refused; an optional non-empty string `tag`; no duplicate `(revisionName, tag)` target). `traffic_exact` then requires exactly one revision with positive traffic: the expected one at exactly 100 %, and a total of 100. It is used for the recovery readback, the manual rollback readback, the post-shift readback and the pre-shift readback. Valid 0 % tagged revisions are accepted. An invalid readback retains or creates the INDETERMINATE lock, invalidates smoke evidence and checkpoint, and never clears the lock. **Tests (`H1`–`H3`, 62 total with the earlier 59):** 33 invalid traffic shapes for automatic recovery, manual rollback (with and without a prior lock) and post-shift activation, plus 5 valid zero-percent shapes that must still recover, roll back and activate.

## Duplicate traffic tag correction (Codex P1 on `290230e6`, #191 comment 7205510648)
**Defect (reproduced):** `TRAFFIC_ARRAY_OK` rejected duplicate `(revisionName, tag)` pairs but allowed the same non-empty tag on different revisions, and `tag_revision()` took the first match. With the baseline at 100 % and two other revisions at 0 % both tagged `a0-dfd49116`, the pre-shift check proceeded to `update-traffic` and manual rollback cleared the INDETERMINATE lock. **Correction:** every non-empty traffic tag must occur at most once in the whole array, whatever the revision: in `TRAFFIC_ARRAY_OK` (recovery, rollback, post-shift and pre-shift readbacks) and in `valid_service_json`, so every service read refuses an ambiguous tag *before* any revision is selected or adopted; `tag_revision()` returns an explicit ambiguity sentinel instead of the first match, and the adoption and post-deploy paths refuse it. Distinct tags on legitimate 0 % revisions and all earlier valid readbacks are unchanged. **Tests `J1`–`J3` (65 total):** four duplicate-tag shapes (two revisions, identical URLs, baseline sharing a tag, three-way) never reach `update-traffic`, `run deploy` or an adoption in the shift, API and bridge flows; the same shapes give INDETERMINATE on recovery, keep the lock on manual rollback and cannot establish a post-shift activation; distinct-tag readbacks still recover, roll back and activate.

**Defect (reproduced with real curl):** neither `curl` call in `a0-smoke.sh` had `-q`, so a `.curlrc` in a default configuration location could add a `url` transfer; the `-K -` bearer header then applied to it.
