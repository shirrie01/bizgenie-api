## 2. Part A — `BG_BRIDGE_ALLOW_FOUNDER_ADDITIONAL_WORKSPACE`
Admits **only** `POST /customer/workspace/brands` (the existing `createAdditionalWorkspace`), exact URL (any query, suffix, other method or sibling route is denied).
- Founder identity only (`BG_BRIDGE_FOUNDER_AUTH_USER_ID`); anonymous 401, other users 403, before IAM.
- Body must equal the pinned body exactly: `BG_BRIDGE_FOUNDER_WORKSPACE_TENANT_ID` (the founder's **existing** owner tenant), `…_BUSINESS_NAME` (trimmed, e.g. `Fonzo`), optional `…_WEBSITE`, `…_CHALLENGE`. Extra/missing/changed fields → 404, no IAM, no upstream. The API still requires the caller to own that tenant.
- **One attempt per bridge process**: the upstream operation is not idempotent (each call creates another project and brand), so a second request answers 409 `FOUNDER_WORKSPACE_ALREADY_ATTEMPTED` before IAM, concurrently included. A lost response is reconciled by `GET /customer/workspace` (listing), never by replay; another attempt needs a deliberate bridge redeploy.
- **Isolated profile**: startup fails if combined with onboarding, recommendations, campaign root, draft workflow, copy, social, video attachment, asset intake, any founder video config, or any broad write flag. It does not open generic bootstrap, select, or any customer write.
- **Fairway key**: no campaign permission exists in this profile. The fixed key `bg-r2-founder-campaign-v1` is namespaced by (tenant, project, actor); the new workspace has a **new project**, so it is a different namespace. The harness proves a same-key Fonzo root succeeds in the new project, replays idempotently, and the same key with Fonzo content in Fairway's scope fails `IDEMPOTENCY_KEY_CONFLICT` with Fairway unchanged. Nothing resets or reuses the spent key.
- **Consequence to approve (D1):** the existing operation provisions the founder's *trusted scope* to the new workspace (`requires_session_refresh`). After it, the founder identity operates in Fonzo; Fairway data is untouched but the Fairway-pinned bridge revisions no longer match that identity, and returning needs the `select` operation, which is deliberately **not** admitted. Use a bridge revision with Fonzo pins from then on.

## 3. Part B — `BG_BRIDGE_ALLOW_FOUNDER_ASSET_INTAKE`
Pins `BG_BRIDGE_FOUNDER_INTAKE_TENANT_ID / PROJECT_ID / BRAND_ID` (the Fonzo scope from A0). Admits only:
| Route | Bridge checks before IAM |
|---|---|
| `POST /customer/assets/uploads` (init) | founder; trusted scope = pin; exact field set `tenant_id, project_id, brand_id, filename, content_type, bytes, rights_confirmed, idempotency_key`; scope fields = pin; `rights_confirmed === true`; type ∈ png/jpeg/webp/mp4; integer bytes 1..33,554,432; safe filename ≤ 200; identifier key; no unknown field (so no client-chosen hash, uses or policy) |
| `PUT /customer/assets/uploads/:uuid/bytes?tenant_id&project_id&brand_id` | founder; exactly those three query keys = pin; `Content-Type` exactly one of the four types; 1..32 MiB body (the 32 MiB boundary is inclusive, 32 MiB + 1 refused by the bridge) |
| `POST /customer/assets/:uuid/complete` | founder; body exactly the pinned three fields |
| `GET/HEAD /customer/assets…` (list, get, preview) | **founder only** and the pinned scope must be in the query (extra keys other than `limit`, `cursor` refused) — this makes previews owner-only at the bridge; the API additionally allows a same-tenant `member` to read, but only the founder identity passes this bridge |
Not admitted: revoke, delete, any other asset write, any other write route. Profile isolation: startup fails with video config/attachment, workspace permission, or broad writes; if draft or root pins are present their scope must equal the intake pin.
**API behaviour relied on (unchanged, covered by the harness):** server SHA-256 and storage read-back; state machine `initiated → quarantined → ready|rejected`; `complete` runs the inspector; scanner failure/timeout leaves the asset quarantined with no usable asset and no preview; an engine labelled `UNSCANNED` is refused unless the API itself is explicitly configured for isolated-staging unscanned mode (a deployment decision, D3, not changed here); a changed rights policy blocks completion; `init` is idempotent by key with an intent hash (changed body → `IDEMPOTENCY_KEY_CONFLICT`); a repeated `PUT` of the same bytes and a repeated `complete` add nothing.
**Upload is not generation or attachment.** An uploaded file becomes a `source_kind='reference'` asset. The campaign layer refuses it as a creative (`CampaignResourceError` for an image/video content item or revision referencing it), no generation job or credit is created, and no route in this change binds it to a variant. Using the artwork *inside* a generated image, video or composition remains a separate scoped design and approval.

## 4. Validated A0 → A1 → A2 sequence and pin handoff
`node scripts/staging/validate-founder-release07.js PRIVATE_ENVELOPE.json` (offline; reads only the file; prints a status, never identifiers).
1. **A0 `profile: "workspace"`** — onboarding-base envelope with only the workspace permission and pins; the workspace tenant must equal the protected Fairway tenant (the founder's owner tenant). Requires three **distinct** GitHub-comment evidence references (`approvalRef`, `independentScopeEvidenceRef`, `rollbackEvidenceRef`) and the private `protectedScope` tuple (Fairway tenant/project/brand/campaign) to compare against.
2. Operator-private: read the new workspace ids from the authenticated founder session (not from GitHub), save Fonzo Brand Brain through the existing onboarding route, obtain the accepted recommendation, build the seven-field body privately and hash it with `scripts/staging/hash-founder-campaign-body.js`.
3. **A1** — the existing `validate-founder-campaign-release.js` with the Fonzo root pins (accepted profile, unchanged).
4. After the single root write, record the campaign id privately.
5. **A2 `profile: "fonzo_a2"`** — draft + copy + social + asset intake. In addition to the release-04 `draft_connections` rules it requires `a1.campaignRoot` (what A1 actually deployed) to equal the A2 root pins **and body hash**, the draft and intake scopes to equal that root scope, a UUID campaign id that is **not** the protected Fairway campaign, Fonzo's project and brand to **differ** from Fairway's, no workspace keys, and the intake flag. Any drift fails closed with a generic error.
**Limits of the validator:** a syntactically valid evidence reference is not proof that an approval exists; equal pins do not prove account ownership. A reviewer must read each referenced comment. "Explicit independent scope evidence" means a separate human-verified readback of the Fonzo tuple from the authenticated session and database by someone other than the author, referenced in `independentScopeEvidenceRef`, **before** any A1/A2 write.
