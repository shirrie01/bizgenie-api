## 2. Part A — `BG_BRIDGE_ALLOW_FOUNDER_ADDITIONAL_WORKSPACE` (durable duplicate protection)
**Review finding resolved (#269 comment 7164949199):** the earlier bridge-memory single attempt could be bypassed by a restart, a second replica, or a lost response followed by a restart. It is **removed**. Protection now lives in the database and is independent of any bridge process.
- **API (`POST /customer/workspace/brands`, same route):** new optional `idempotency_key` (1–200 chars, `^[A-Za-z0-9][A-Za-z0-9._:-]*$`). With a key, the project and brand ids are `sha256(["customer-workspace.v1", owner, tenant, key])`. The existing owner check and per-owner advisory lock run first; if those primary keys already exist the stored workspace is returned (nothing is inserted), so concurrent instances serialise and exactly one inserts. Replays re-run the trusted-scope step, which is what recovers a lost response. The same key with a different business name is refused (`idempotency_conflict`); a different owner or non-owner gets the unchanged `unauthorized` answer, and the owner is part of the derivation so keys cannot collide or leak across users. **No migration:** the existing primary keys of `projects` and `brand_brains` are the durable single-use record. Without a key the operation is unchanged (a new workspace per call). Limit: on a replay the website and challenge fields are not re-applied or compared (the pinned bridge body fixes them).
- **Bridge:** admits only `POST /customer/workspace/brands`, founder identity only, body must equal the pinned body **including the pinned key** (`BG_BRIDGE_FOUNDER_WORKSPACE_IDEMPOTENCY_KEY`; required; must not be the fixed campaign key). The bridge holds no creation state; every replay of the pinned body is forwarded unchanged. If an API revision does not know the field its strict schema refuses the request, so the failure mode is "nothing created", never a duplicate.
- **Isolated profile:** startup fails if combined with any other founder or broad write permission, any founder video config, or asset intake. No campaign permission: Fairway's spent fixed key is untouched, and the new project is a new idempotency namespace (proved in the harness; the same key with Fonzo content in Fairway's scope conflicts, Fairway unchanged).
- **Lost-response and recovery procedure (founder scope):**
  1. Never create a second workspace by hand. A second request with the **same pinned key** is the safe retry; it returns the same ids.
  2. To see what exists without writing: `GET /customer/workspace` (read-only) returns `selection_required` with every workspace the founder owns; read the ids privately, never into GitHub.
  3. After creation the founder's trusted scope is Fonzo (the operation provisions it; the session needs a refresh). Fairway data and its campaign are untouched, but Fairway-pinned bridge revisions no longer match that identity.
  4. Returning to Fairway (or back) is the existing `POST /customer/workspace/select` operation, which this change **deliberately does not admit**. It works at the API layer (harness test 6). Admitting it, or an operator-run equivalent, needs a separate, scoped, reviewed approval — not part of this PR.
  5. Use a different `idempotency_key` only to intentionally create another workspace, with a new approval.

## 3. Part B — `BG_BRIDGE_ALLOW_FOUNDER_ASSET_INTAKE`
Pins `BG_BRIDGE_FOUNDER_INTAKE_TENANT_ID / PROJECT_ID / BRAND_ID` (the Fonzo scope from A0). Admits only:
| Route | Bridge checks before IAM |
|---|---|
| `POST /customer/assets/uploads` (init) | founder; trusted scope = pin; exact field set `tenant_id, project_id, brand_id, filename, content_type, bytes, rights_confirmed, idempotency_key`; scope fields = pin; `rights_confirmed === true`; type ∈ png/jpeg/webp/mp4; integer bytes 1..33,554,432; safe filename ≤ 200; identifier key; no unknown field (so no client-chosen hash, uses or policy) |
| `PUT /customer/assets/uploads/:uuid/bytes?tenant_id&project_id&brand_id` | founder; exactly those three query keys = pin; `Content-Type` exactly one of the four types; 1..32 MiB body (the 32 MiB boundary is inclusive, 32 MiB + 1 refused by the bridge) |
| `POST /customer/assets/:uuid/complete` | founder; body exactly the pinned three fields |
| `GET/HEAD /customer/assets…` (list, get, preview) | **founder only** and the pinned scope must be in the query (extra keys other than `limit`, `cursor` refused) — this makes previews owner-only at the bridge; the API additionally allows a same-tenant `member` to read, but only the founder identity passes this bridge |
Not admitted: revoke, delete, any other asset write, any other write route. Profile isolation: startup fails with video config/attachment, workspace permission, or broad writes; if draft or root pins are present their scope must equal the intake pin.
**API behaviour relied on (unchanged, covered by the harness):** server SHA-256 and storage read-back; state machine `initiated → quarantined → ready|rejected`; `complete` runs the inspector; scanner failure/timeout leaves the asset quarantined with no usable asset and no preview; an engine labelled `UNSCANNED` is refused unless the API itself is explicitly configured for isolated-staging unscanned mode (a deployment decision, D3, not changed here); a changed rights policy blocks completion; `init` is idempotent by key with an intent hash (changed body → `IDEMPOTENCY_KEY_CONFLICT`); a repeated `PUT` of the same bytes and a repeated `complete` add nothing.
**Upload is not generation or attachment.** An uploaded file becomes a `source_kind='reference'` asset. The campaign layer refuses it as a creative (`CampaignResourceError` for an image/video content item or revision referencing it), no generation job or credit is created, and no route in this change binds it to a variant. Using the artwork *inside* a generated image, video or composition remains a separate scoped design and approval.
