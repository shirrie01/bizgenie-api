**Q1 — Unchanged full payload: yes.** An authorized member's PUT succeeds when effective `name` and `identity.description` equal the current stored values. Input schema trims leading/trailing whitespace before comparison; comparison is then exact, case-sensitive JavaScript string equality. Internal whitespace/case is not normalized. Stored legacy whitespace is not independently normalized. Missing description and absent identity both compare as undefined; omitting an existing description is deletion and is denied. Name remains required: this is replacement PUT, not PATCH. Carry unchanged name/description and other fields you want preserved; optional omitted sections are removed under existing semantics.

**Q2 — Denial is atomic, no silent dropping.** Customer `PUT /customer/workspace/brand-brain` returns HTTP **403**:
```json
{"status":"failed","error":{"code":"BRAND_BRAIN_WRITE_FORBIDDEN","message":"Current workspace-owner authority is required for business identity changes"}}
```
There are **no details/path fields** for this policy error. The whole request is rejected: no unrelated fields, timestamps or version are committed. This is not `WORKSPACE_NOT_AUTHORIZED` (the separate onboarding endpoint's code). Valid customer writes retain HTTP200 `{"status":"ready","brand_brain":{...}}`.

**Q3 — Nonmember/revoked: not completely unchanged.** Brand Brain customer PUT now returns the same **403 `BRAND_BRAIN_WRITE_FORBIDDEN`** for failed current membership or transaction-bound authorization (previous preliminary workspace refusal was400). Do not infer from this code alone that the caller is still a member. Brand Brain GET is unchanged: a verified actor with unauthorized selected workspace receives **400 `WORKSPACE_VALIDATION_ERROR`**, `status:"failed"`, details `[{"path":"trusted_scope","code":"unauthorized","message":"Workspace selection is not authorized"}]`. Missing trusted scope is also400 validation; invalid/missing bearer authentication is401 `AUTHENTICATION_REQUIRED`. The narrow missing-Brain-after-selection race retains existing400 validation. Revocation/demotion before the write's authority lock denies; after lock it waits for the authorized transaction, then later writes deny. Delivered responses cannot be recalled. Re-read authorized workspaces on refusal; role hints can be stale.

**Q4 — Capability hint: no new field.** GET Brain and workspace envelopes are unchanged. Use existing workspace `membership_role` for UI guidance only; the server transaction is authoritative. Members retain editing of unrelated Brain fields even though onboarding progress/completion writes remain owner-only. Do not make the whole Brain read-only merely because onboarding is view-only.

**Q5 — Exactly `name` and `identity.description`.** Other `identity.*` fields (mission, vision, values, positioning) and unrelated Brain sections remain outside this owner-only field policy. Customer correction and admin replacement routes are guarded. Customer bootstrap initializes owner membership/Brain; retries do not overwrite existing identity. Additional-workspace creation requires owner membership and now locks it through commit. Campaign/generation/onboarding-preference code does not add another identity correction path. Raw repository upsert is a trusted internal/seeding primitive, not a customer-authorized HTTP path; privileged direct SQL is outside application policy.

**Q6 — Concurrency: server guard added; no client CAS.** Customer PUT still strips/ignores client metadata as an authority/version token and increments server version. Inside one transaction the backend locks current membership/project and Brain, then compares the locked row to its earlier server snapshot. A changed snapshot yields HTTP **409**:
```json
{"status":"failed","error":{"code":"BRAND_BRAIN_VERSION_CONFLICT","message":"Brand Brain changed; reload before saving"}}
```
No details/current_version is supplied; do not reuse onboarding's VERSION_CONFLICT decoder. Reload and reconcile before resubmission. Overlapping writes using the same server snapshot cannot both commit. A stale member/admin payload cannot restore a changed protected field: depending on timing it receives403 (already stale when server read starts) or409 (row changes after server read). **Sequential stale client payloads are not generally detected** for owner-authorized identity changes or unrelated fields: no new expected_version/ETag or idempotency guarantee is introduced. Lost-response/503 Brain saves remain unconfirmed; do not claim exactly-once retry as with onboarding.

**Q7 — Onboarding rechecks remain required and unchanged.** Architecture A / `workspace-onboarding.v1` remains intact. It stores sector/channel/draft separately, does not write Brain, and requires owner writes and explicit completion. Current business-fact validation still applies on later completed-profile writes, with transaction-time validation for PostgreSQL. `422 ONBOARDING_INCOMPLETE` retains `status:"failed"`, and `error.details` entries `{path:"business_name"|"description",code:"required",message:"Required to complete onboarding"}` (plus other missing-answer paths). Owner changes, bootstrap placeholders/seeded descriptions or missing facts can still make current completion invalid; this policy is not an immutable freeze or an authorship ledger. Do not automatically convert inferred provenance or promise completion forever from an earlier status.

**Q8 — Admin restriction is separate; customer bootstrap unchanged.**
- Customer app continues using bearer-authenticated `/customer/workspace/brand-brain`, never an admin key. Search of current web #49 production `src` found no `/_admin/` callers; its App.jsx uses the customer route. Admin restriction itself does not change that route, but Q2/Q3/Q6 describe real customer-visible policy/error changes, so “only member denial changes” is too narrow.
- Admin-key-only `PUT /_admin/brand-brains/:brandId` creation/identity changes return403 **`{"error":{"code":"BRAND_BRAIN_WRITE_FORBIDDEN","message":"Current workspace-owner authority is required for business identity changes"}}`**, without customer `status`. Missing/wrong admin key still returns403 `{"error":"Forbidden"}`. Unrelated admin corrections/read responses remain unchanged. Admin overlapping stale snapshot409 uses the same error object as Q6, without `status`; existing `409 BRAND_PROJECT_CONFLICT` remains distinct.
- Customer `POST /customer/workspace/bootstrap` keeps **201** for successful new creation **and existing single-workspace reuse**, body `{"status":"ready","workspace":{tenant_id,tenant_name,project_id,project_name,brand_id,brand_name,brand_status,membership_role}}`; new bootstrap membership_role is owner. When scope provisioner is configured, existing `requires_session_refresh` boolean is included; refresh when true. With multiple existing workspaces, bootstrap returns201 `{"status":"selection_required","workspace":null,"workspaces":[...]}` rather than choosing silently. Existing401 authentication,400 validation and503 provisioning/unavailability paths are unchanged; scope-provisioning failure uses `WORKSPACE_PROVISIONING_UNAVAILABLE`. Bootstrap is not an admin-route operation or a new idempotency-key API.
- A rejected admin/recovery action commits no identity deletion/revert. Existing saved values remain; an attempted operator repair may remain unapplied. Display actual saved facts; do not claim repair succeeded or invent placeholders. If required facts remain absent, retain incomplete guidance and ask the verified workspace owner to correct them through the customer route. No customer-specific “admin failed” response/event was added.
