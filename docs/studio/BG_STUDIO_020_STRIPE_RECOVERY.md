# BG-STUDIO-020 — fenced Stripe-event recovery

26 October 2026. IMPLEMENTED LOCAL / MOCK-TESTED with disposable PostgreSQL; no live Stripe calls, production composition or endpoint activation.

`FencedStripeBillingRepository` is an opt-in subclass of the existing durable billing repository. New additive draft SQL adds claim_token, attempt_generation and claimed_at to existing stripe_webhook_events; historical SQL is unchanged. Begin verifies immutable event ID/type/mode/hash. Ordinary duplicate processing still returns503; **explicit internal recovery**, not lease expiry, replaces the token and increments generation. Processed events replay unchanged.

`StripeSubscriptionService.recoverVerifiedEvent(event)` is internal-only and refuses a non-fenced repository or a different repository behind BillingService. The normal signed-webhook ingress never accepts a customer recovery flag. The event must already be obtained and authenticated through the existing signature/verified Stripe mechanism; this method does not authenticate arbitrary customer JSON.

AsyncLocalStorage binds the handler to its durable event token. Every financial `withTransaction` on that same repository checks the processing event/token under a row share lock, held through commit. Claim replacement takes an exclusive row lock. A slow old handler may finish an already authorized transaction before replacement; it cannot start another financial transaction or finalize/abandon after replacement. Existing unique ledger/monthly-period identities and lifecycle ordering provide replay protection after partial progress. Recovery reads canonical current Stripe state through existing service logic; it does not create/cancel/modify subscriptions or guess refunds.

Local evidence:27/27 PostgreSQL billing integration tests, including token takeover/identity conflict, crash after monthly grant and before event completion, restart recovery with exactly one grant, and a slow old handler fenced after replacement completes. Existing Stripe unit mocks30/30. Full Node22/disposable PostgreSQL suite753/753, zero skipped at this checkpoint.

Limits: the effect and event-finalization steps remain separate existing transactions, made replay-safe by fencing and existing durable unique identities, not represented as one atomic external transaction. Recovery is explicit and currently internal, not an unattended scheduler. It must be operationally audited and rate-limited before activation. **Mixed deployment with old unfenced workers is unsafe**: drain/quiesce old event workers and verify every effect uses the fenced repository before enabling recovery. Migration alone does not enforce financial fencing against older application binaries. No implementation is activated in current production composition. Test credentials/configuration and existing verified-event contracts remain prerequisites.

Rollback: disable recovery composition/entrypoint and stop new recovery activity; preserve event tokens, attempts, mappings and ledger. Do not delete/reset claims or reverse successful grants. Existing binaries ignore new nullable/default columns, but must not run concurrently with active fenced recovery. Any shared migration, deployment, Stripe test-clock/real callback or operational reconciliation needs separate founder approval.
