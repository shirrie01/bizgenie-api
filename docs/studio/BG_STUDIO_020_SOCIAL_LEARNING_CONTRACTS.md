## Social contract and required durable implementation

`src/social-contracts/contract.js` validates token **references**, expiry/revocation, workspace/brand/account, server-approved required scopes, owner authority, explicit publishing consent, current approval/revision/schedule/rights and expected campaign version. No raw token field is accepted. OAuth callback validation binds hashed state, workspace, expiry and PKCE challenge, returning an expected-unconsumed nonce CAS requirement. It does **not** consume a nonce or exchange a code; a durable transaction must do that before exchange. Token encryption/key management is not provisioned.

Dispatch identity hashes tenant/project/connection/account/campaign/variant/revision/approval/schedule. `dispatchTransition` rejects stale fences, refuses another send after an uncertain outcome, accepts only definitive failure or matching provider success, and separates platform_api evidence from manual customer attestation. MockSocialProvider demonstrates reconciliation after timeout without a second submit. This is a deterministic reference adapter, **not a supported live Instagram/Facebook/LinkedIn/TikTok/YouTube connector**.

Required outbox architecture: transactionally lock current connection version/token reference and campaign approval/revision/schedule/rights; insert one dispatch under unique destination+revision+schedule identity; claim with durable monotonic fence/token; record sending boundary before external call; persist provider operation/publication reference; commit verified result/history and projection atomically. Pre-call work can be reclaimed with a new fence. After sending/timeout, hold reconciliation-required and retrieve provider status using stable identity; never infer failure from timeout or automatically repost. Every retry/finalization must check the current durable fence. Disconnect/revocation denies new dispatch and refresh; already in-flight calls need explicit cancellation/reconciliation semantics. Avoid conflating new verified-platform history with existing manual-publication confirmation routes.

No outbox migration/SQL store/scheduler or token-refresh worker is implemented in this checkpoint. Use the established PostgreSQL/ledger fencing patterns from this branch; do not reuse generation billing job identities for publications or duplicate its paid debit semantics. A reference state machine is not crash-safe scheduling. Before activation, implement/test the outbox and projection binding with two PostgreSQL worker instances and all crash boundaries.

External prerequisites by platform: approved developer app, exact current OAuth redirect origins and scopes, correct account/page/channel ownership selection, permissions/app-review status, publish/status-reconciliation endpoints, token expiry/refresh/revocation behaviour, media formats/limits and API quotas. Current authoritative provider documentation/credentials/app-review state were not accessible here; exact external scope names are **UNKNOWN**, not invented from memory. requiredScopes is server-supplied and fail-closed, including URL-shaped provider scopes. Founder must authorize each controlled connection/publishing test separately.

## Performance/learning contract

`src/performance-evidence/contract.js`: immutable `performance-observation.v1` with tenant/project/brand/campaign/variant/publication, authoritative objective/platform, organic|paid attribution, metric/unit/value, explicit [from,to) period, observation time, verified platform source/account/record identity, correction/retraction chain and canonical fingerprint. Connector authorization callback is mandatory; no public caller-supplied 'verified' flag is accepted as evidence. Binding requires publication time <= period start. Future/malformed periods, missing objective/attribution, wrong tenant/account/publication/platform, incompatible units and conflicting IDs fail. This is intentionally conservative; partial/cumulative periods need a separately reviewed measurement contract.

Reference registry keeps platform data apart from existing `customer_attestation` registry. Corrections supersede an exact scoped predecessor; retraction removes evidence rather than fabricating zero. Snapshots explicitly return unavailable for missing/retracted/stale data with a server-specified age policy and hash. Equal-duration non-overlapping comparable periods can generate `evidence-recommendation.v1` observed change, exact source fingerprints, `causal_claim:false`, `confidence:observed_change_only`, and required customer acceptance. Zero baseline gives null percentage, never infinity or a made-up rate. Customer feedback schema records actor/scope/decision; no Brand Brain or strategy mutation follows automatically.

The registry is explicitly **process-local reference code**; durable ingestion, source-authenticated adapters, feedback persistence, corrections/retraction auditing, recommendation access control, paid/organic joins and future-strategy wiring are **not implemented**. No mounted ingestion/learning endpoint or measured conversion claim. Reuse #204 objective/interval/provenance work only after confirming its current branch and trustworthy source joins; do not overwrite it.

Deterministic synthetic tests cover source denial, foreign scope, missing metadata, customer-attestation rejection, replay/conflicting intent, correction/retraction, stale/unavailable snapshots, invalid units/future values, comparable periods/zero baseline, OAuth nonce/PKCE/expiry/scope, current authority, revoked connection, stale fences, uncertain dispatch and provider reconciliation. They establish contract behaviour, not platform API or production readiness.
